# Plan: Persistent Cloudflare Domains and Reliable Demo Deployment

## Goal

Add stable Cloudflare-managed subdomains for both Azure Container Apps, bind them to Azure-managed TLS certificates, and make the Terraform demo reproducible after the deployment and onboarding failures observed during testing. Add a complete reusable `terraform.tfvars.example`, deterministic preflight/verification commands, and a deliberately demo-only output artifact containing deployment URLs and requested credential values.

Implementation must not start until the Cloudflare zone/domain ownership decision in **Open Questions** is answered.

## Current State

- Terraform manages an existing resource group lookup, one Log Analytics workspace, one Container Apps environment, and the ERPBridge and MockERP apps. There is no Cloudflare provider, DNS resource, custom-domain resource, certificate resource, or domain input: `terraform/main.tf:1-28`, `terraform/main.tf:23-168`, and `terraform/main.tf:170-280`.
- Application URLs are derived from the Azure Container Apps environment default domain, so they change when the environment is destroyed and recreated: `terraform/locals.tf:27-28`. The current outputs expose only those generated URLs: `terraform/outputs.tf:1-45`.

This was added after Azure rejected a reused suffix. The safer design is to let Azure assign a unique revision suffix instead of using a secret-derived suffix.

- The operational Make targets perform health and MCP checks, but `verify-ingress` invokes `list-warehouses` while OpenAPI-generated tool names use underscores, such as `list_warehouses`: `Makefile:45-102`.
- The deployed ERPBridge image previously lacked the server-side API-probe route expected by the installed `bridgectl`; direct control-plane tool list/apply and direct tool invocation still worked. The plan must pin a server/CLI-compatible image and add a compatibility check before onboarding.
- The MockERP source provides a static OpenAPI contract at `/home/nimendra/Documents/Projects/mockerp/openapi.yaml`. The FastAPI app in `/home/nimendra/Documents/Projects/mockerp/main.py:29-44` also exposes the generated `/openapi.json` route when the container is healthy. The static contract contains 81 path templates and is the more reproducible onboarding input.
- No `Tickbook`, `TickBook`, or similarly named infrastructure directory was found under `/home/nimendra/Documents/Projects`; `Booktrack-CLI` exists but contains no Terraform or Cloudflare infrastructure. There is therefore no local Tickbook pattern to copy.
- Azure's managed-certificate guidance requires a subdomain CNAME to point directly to the Container App generated hostname and an `asuid.<subdomain>` validation TXT record. It warns that an intermediate CNAME such as a proxied Cloudflare record blocks issuance/renewal. Source: <https://learn.microsoft.com/en-us/azure/container-apps/custom-domains-managed-certificates>.
- AzureRM 5.2.0 exposes `azurerm_container_app_environment_managed_certificate` and `azurerm_container_app_custom_domain`, but the custom-domain resource does not accept a managed-certificate ID as an input; the provider's automatic managed-certificate binding remains unreliable. AzureRM issue #27362 documents the missing binding behavior: <https://github.com/hashicorp/terraform-provider-azurerm/issues/27362>. The selected implementation will use AzAPI for the explicit certificate binding.
- Cloudflare's current Terraform provider uses `cloudflare_dns_record` with `zone_id`, `name`, `type`, `content`, `ttl`, and `proxied`; API-token authentication is preferred through `CLOUDFLARE_API_TOKEN`. Sources: <https://registry.terraform.io/providers/cloudflare/cloudflare/latest/docs/resources/dns_record> and <https://registry.terraform.io/providers/cloudflare/cloudflare/latest/docs>.

## Decisions

1. **Use direct CNAMEs with Cloudflare DNS-only records.** Each hostname will point directly to its corresponding Azure Container App generated FQDN, with `proxied = false`. Cloudflare proxying is rejected because Azure managed-certificate validation and renewal require a direct CNAME.
2. **Use Azure-managed certificates with CNAME validation and an explicit AzAPI binding.** Terraform will manage the Container App custom-domain resource and environment managed certificate, while Cloudflare manages the direct CNAME and `asuid.<subdomain>` TXT validation record. AzAPI will PATCH each Container App's `configuration.ingress.customDomains` with the managed certificate ID and `SniEnabled` binding. Bring-your-own certificates are out of scope.
3. **Manage records in an existing Cloudflare zone by default.** Terraform will accept an explicit `cloudflare_zone_id` and use `CLOUDFLARE_API_TOKEN` from the process environment. It will not purchase/register a domain. Creating a Cloudflare zone can be added only if the user confirms that the domain is already registered and nameservers can be delegated.
4. **Keep custom domains optional for reuse, but require all domain inputs together.** With custom domains disabled, the deployment continues to work on Azure default hostnames. With them enabled, both ERPBridge and MockERP hostnames, the zone ID, and DNS records are created as one coherent feature; partial configuration fails during validation.
5. **Expose custom URLs as the canonical application URLs.** Outputs and generated onboarding manifests will use the custom ERPBridge URL, custom `/mcp/` URL, and custom MockERP URL when enabled. Azure-generated URLs remain separate diagnostic outputs.
6. **Let Azure generate revision suffixes.** Remove the secret-hash suffixes and the `ignore_changes` workaround. Secret changes will still force new revisions through the secret-name changes, while Azure owns unique revision naming and avoids the duplicate-suffix failure.
7. **Validate MockERP credentials before Azure creates a revision.** Require valid JSON containing at least one supported identity record and add a resource precondition that the ERPBridge `erp_primary_key` matches the first MockERP API credential in the documented `token <api_key>:<api_secret>` format. This turns the previous CrashLoopBackOff into a plan-time error.
8. **Make public MockERP ingress an explicit opt-in.** Restore the default rejection of `0.0.0.0/0`; add a clearly named demo-only opt-in if unrestricted testing is still needed. The reusable example will use a real client CIDR input, not a documentation IP.
9. **Keep secrets out of normal output but provide an explicit demo export.** Mark credential outputs sensitive and add a post-apply export script that writes the requested URLs, image/value metadata, and Terraform credentials to an ignored, mode-`0600` JSON artifact without printing it. Raw bridgectl-created MCP tokens can only be captured when first created, so a separate token-creation wrapper will record them once; `bridgectl token list` cannot recover them.
10. **Treat SQLite persistence as a separate decision.** Stable DNS does not preserve the ERPBridge registry or MockERP data. This plan will document that destroy/recreate resets those stores and will provide deterministic token/tool re-onboarding. Azure Files-backed persistence is not included unless the user confirms it.
11. **Use AzAPI for the managed-certificate binding.** Add the `azure/azapi` provider and pin the supported `Microsoft.App/containerApps@2025-07-01` API version for the `customDomains` PATCH. Keep the AzAPI body limited to the two domains managed by this stack, and document import/state precautions if other custom domains are later added to either app.

## Scope

### In scope

- Cloudflare provider configuration and DNS-only CNAME/TXT records for two subdomains.
- Azure Container Apps custom-domain resources, Azure-managed certificates, and explicit AzAPI certificate bindings.
- Canonical custom URL outputs and custom-domain verification.
- Credential-shape validation, safe revision naming, explicit ingress policy, and compatibility preflight.
- Complete reusable `terraform.tfvars.example` with non-secret values and environment-variable instructions.
- Demo-only output export, MCP-token capture helper, file permissions, and Git ignore rules.
- Make targets/scripts/docs for init, plan, apply, health, DNS/TLS checks, MCP checks, and OpenAPI onboarding.
- Deterministic OpenAPI manifest generation using the deployed/custom MockERP URL and safe onboarding verification.

### Out of scope

- Domain purchase, registrar changes, or nameserver delegation without a separate confirmed action.
- Cloudflare proxying, load balancing, Workers, tunnels, or WAF policy.
- Bring-your-own TLS certificates.
- Persistent Azure Files storage for SQLite unless separately approved.
- Automatic creation or recovery of raw MCP tokens after the server database is destroyed.
- Deleting or rewriting the existing untracked generated manifests without an explicit cleanup decision.
